# Specification: Feature-Based Architecture & Settings Modernization

## 1. Overview
The goal is to transition the current flat `components/` structure to a domain-driven, feature-based architecture. This improves scalability and maintainability by grouping related logic, UI, and types together. Additionally, the Settings module will be refactored to use a more robust Design Pattern (Factory/Dispatcher split with a Central Registry) to manage dynamic configuration panels.

## 2. Functional Requirements

### 2.1 Directory Restructuring
Migrate all components from the flat `components/` directory into domain-specific subfolders. This leverages Nuxt 3's directory-based auto-importing.
- **`components/Trades/`**: `TradeForm`, `TradeList`, `TradeDataTable`, `TradeStats`, `TradeGallery`, `TradeReview`, `TradeScreenshots`, `TradeSummaryCard`.
- **`components/Analytics/`**: `AnalyticsDashboard`, `TradingViewChart`, `CalendarRange`.
- **`components/Layout/`**: `AppSidebar`, `PaneNav`, `CollapsibleSection`.
- **`components/Settings/`**: `ChipPanel`, `ChipSelect`.
- **`components/UI/`**: `Combobox`, `DeleteConfirmationModal`, `SaveControls`, `ToastNotification`.

### 2.2 Component Modernization
- **Auto-import Names:** Update all templates and script references to use the new prefixed names generated by Nuxt (e.g., `<TradeForm />` becomes `<TradesForm />`).
- **Configuration:** Ensure `nuxt.config.ts` is configured to scan these nested directories recursively.

### 2.3 Settings Module Refactor
- **Central Registry (`SettingsRegistry.ts`):** Implement a registry that maps setting keys (e.g., 'Strategies', 'Psychology') to their respective UI components and metadata.
- **Settings Factory (`SettingsFactory.tsx`):** Implement a factory that instantiates components based on the registry.
- **Dispatcher/Factory Split:** Decouple the logic that determines *which* component to show from the logic that *renders* it.

## 3. Non-Functional Requirements
- **Type Safety:** All new registry and factory logic must be strictly typed using TypeScript.
- **Performance:** Ensure the refactor does not negatively impact build times or bundle size.
- **Zero Behavioral Change:** The end-user experience must remain identical to the current implementation.

## 4. Acceptance Criteria
- All components are relocated to their respective feature folders.
- The application builds successfully without broken component references.
- The `settings.vue` page correctly renders all configuration panels using the new Factory/Registry architecture.
- Existing Vitest tests pass (after updating component names/paths).
- All pages (`dashboard.vue`, `settings.vue`, `index.vue`) render correctly in the browser.

## 5. Out of Scope
- Adding new features or modifying the existing UI/UX design.
- Significant refactoring of the `server/` or `composables/` directories.
- Database schema changes in Google Sheets.
